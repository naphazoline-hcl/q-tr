# P6: 戦略レポート（提出用 `README.md`）と最終検収

## 0. 出力形式（厳守・最初に読め）

- 成果物はコードブロックに埋め込まず、**Write で実ファイルとして作る**（§0.5 の作業規約に従う）。
- 次の2ファイルを `deliverables/` に作る:
  - `README.md` … 提出用の戦略レポート（§1 の構成）
  - `RESULTS.md` … 実測数値の転記表（空欄つき雛形・検証手順つき）
- 成果物を読み込む React Web アプリを作り、**ファイルごとの全文コピー・個別ダウンロード**と
  **JSZip による一括ZIP（`report_package.zip`）**を提供する。
- 受け入れチェック（§4）の結果は**最終報告に簡潔に**書く。
- すべて日本語で出力（コード内コメントのみ英語可）。不明点は質問せず Assumptions 節に記録。
- **数値の捏造は絶対禁止**。実測値の転記欄は初回メッセージの **【実測結果】** にある数字だけを使い、
  指示に無い数値は `{要実行}` と書く。

## 0.5 作業の進め方（タイムアウト対策・厳守）

**着手前に必ず全文を取得して従え:**
`https://raw.githubusercontent.com/naphazoline-hcl/q-tr/main/v0/prompts/P0_作業規約.md`

要点（全文と重複するが必ず守る）:
- **ツールを呼ばずに応答を終えるとターン終了扱い。** 待つだけ・確認だけの文章で終えない。
  待つときは Bash で `sleep 30` を実行する。
- バックグラウンドのコマンドは末尾に `echo __DONE__` を付け、`__DONE__` の出力で完了を判定する
  （状態表示は当てにしない）。
- 1回の応答は1〜2分・合計200行まで。大きなファイルは骨格 → Edit で書き足し、設計を先に完成させない。
- 最初に Bash で `date +%s > /tmp/turn_start`。経過22分で新規作業を止め、25分までに最終報告
  （完了・未完了・次にやること）。
- 中断していたら最初からやり直さず、既存ファイルを確認して続きから再開する。
- 質問して止まらない。不明点は前提を置いて進め、最終報告に書く。

## 1. `README.md` の構成（戦略レポート）

### 仮説（なぜ勝てるはずか）
- 採点式（5分位・片道0.1%・年率Sharpe）から導かれる含意: **順位だけが効き、回転率が支配する**。
- 低速プレミアム（規模・流動性・クオリティ・低リスク）を土台にし、
  機械学習は長期平均ラベルで「数ヶ月スケールの優劣」を学ばせる。
- セクター中立化と局面配分で 2020〜2021 年型のグロース相場への脆さを抑える。

### 処理（何をどう実装したか）
1. 特徴量（`FEATURES.md` の要点を要約。列数・ブロック・因果性の確保方法）
2. ラベル設計（k 平均・クリップ・purge の理由）
3. モデル（LightGBM + アンサンブル構成・seed・カテゴリ特徴の扱い）
4. 合成（ブロック重み・モデル重み・セクター中立・平滑化 span）
5. 推論（`submission.py` のメモリ・時間対策）

### 検証方法（Valid のラベル選択に使っていないことの明示）
- 方針決定は Train 内 purged walk-forward（2010〜2015）で行った。
- Valid は確認のみ。初回メッセージの実測結果に記載の手順で再現できる。

### 実測（【実測結果】の転記・捏造禁止）
- Train OOS の表、Valid の表（Sharpe / グロス / コスト / 回転率 / RankIC / 年別）
- どのように申告値と突き合わせたか（`tools/score.py` の JSON との突合手順）

### 実行方法
```bash
python strategies/v0_multifactor/train_v2.py --strategy strategies/v0_multifactor   # 学習
python evaluate_script.py --submission strategies/v0_multifactor                    # 採点
```

### 限界と改善案
- 残っている弱点（年別・局面別）と次の打ち手（3つまで）。
