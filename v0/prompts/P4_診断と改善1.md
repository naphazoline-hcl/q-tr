- 成果物はコードブロックに埋め込まず、**Write で実ファイルとして作る**。骨格（全体構成と空の関数）→
  Edit で機能追加、の順で少しずつ書く（§0.5 の作業規約に従う）。

- 受け入れチェック（§4）の結果は**最終報告に簡潔に**書く（長くなる場合は `REPORT.md` に分けてよい）。
- **25分で完成しない場合は、完成したファイルだけでも先に作る**。
- すべて日本語で出力（コード内コメントのみ英語可）。不明点は質問せず Assumptions 節に記録。
- **数値の捏造禁止**。実測できない改善効果の主張は書かない。

## 0.5 作業の進め方（タイムアウト対策・厳守）

**着手前に必ず全文を取得して従え:**
`https://raw.githubusercontent.com/naphazoline-hcl/q-tr/main/v0/prompts/P0_作業規約.md`

要点（全文と重複するが必ず守る）:
- **ツールを呼ばずに応答を終えるとターン終了扱い。** 待つだけ・確認だけの文章で終えない。
  待つときは Bash で `sleep 30` を実行する。
- バックグラウンドのコマンドは末尾に `echo __DONE__` を付け、`__DONE__` の出力で完了を判定する
  （状態表示は当てにしない）。
- 1回の応答は1〜2分・合計200行まで。大きなファイルは骨格 → Edit で書き足し、設計を先に完成させない。
- 最初に Bash で `date +%s > /tmp/turn_start`。経過22分で新規作業を止め、25分までに最終報告
  （完了・未完了・次にやること）。
- 中断していたら最初からやり直さず、既存ファイルを確認して続きから再開する。
- 質問して止まらない。不明点は前提を置いて進め、最終報告に書く。

## 1. タスク

初回メッセージ末尾の **【実測結果】** を読み、弱点を分析して改善版を作る。
改善版は **Train 内 purged walk-forward で改善し、Valid でも悪化しない** ことを狙う。

変更できる範囲:

1. `alpha_v2.py` の特徴量ブロック追加・削除、`walkforward_config.json` の重み・パラメータ
2. ラベル設計（`k` の組み合わせ・クリップ幅・ボラ割・ランク化）の変更
3. セクター中立化の強弱（`sector_weight`、`sector_neutral` の切替）
4. 平滑化 `smoothing_span` の変更（`walkforward_config.json` 側）
5. ファクター側の新ブロック追加（ただし特徴量は `alpha_features.py` の範囲内で）

**API 契約は維持**すること（`build_features` / `make_label` / `fit_model` / `predict_signal`、
`walkforward_config.json` のキー構成）。ローカル側は同じコマンドで検証する:

```bash
python tools/walkforward.py --strategy strategies/v0_multifactor --module alpha_v2 --json work/reports/improve1.json
python tools/score.py --submission strategies/v0_multifactor --split train
python tools/score.py --submission strategies/v0_multifactor --split valid
python tools/check_lookahead.py --submission strategies/v0_multifactor --runtime
python tools/check_truncation.py --strategy strategies/v0_multifactor --module alpha_v2 --cut 2014-06-30
```

## 2. 診断の読み方（実測結果の見方）

- 年別 Sharpe で **特定の年に崩れる**場合はレジーム依存（過学習ではなく構造的問題）。
  ブロック配分・マクロ局面・低リスク寄与を見直す。
- グロスは高いがコストで負ける場合は**回転率**が原因。
  ラベルを長期化（k を大きく）・平滑化を強く・モデル寄与を下げる。
- RankIC は高いが Sharpe が低い場合は **Q2〜Q4 の分位リターン**を見る。
  両端だけが当たり、中央が逆に動くモデルは回転率だけを抬げている。
- Train OOS で改善するが Valid で悪化する場合は **2016年以降の構造変化**
  （低金利・グロース優位・マクロ環境）への過適合。Valid の一部分ではなく
  Train OOS の全期間で安定することを優先する。
- 特定ブロックを外したときに改善する場合は、そのブロックの定義を見直す
  （バリューの基準そろえ・セクター偏りが典型原因）。
