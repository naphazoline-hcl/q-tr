# v0.app 運用計画（Stock Competition 2026 / 高精度化サイクル）

> 卒論ディレクトリで確立した運用（プロンプトを GitHub 公開リポジトリに置き、初回メッセージで
> URL を渡す／成果物は Web アプリの ZIP ダウンロードで回収する）をこのコンペ用に移植したもの。
> リポジトリ: https://github.com/naphazoline-hcl/q-tr （公開）

## 0. プラットフォーム制約と対策（確定事項・再調査しない）

| 項目 | 制約 | 対策 |
|---|---|---|
| 長文入力 | v0 は長文を直接貼れない | プロンプトは `v0/prompts/*.md` に置き、初回メッセージで URL を渡す |
| 取得可能URL | **公開 URL のみ**（private は不可） | リポジトリは public。個人情報・学習済みモデルは push しない |
| メッセージ数 | 1セッション **1〜3通** | 1セッション1成果物。修正も新セッションで（初回メッセージ末尾に修正指示） |
| 作業時間 | 1メッセージ **25分まで**（fastモードで中規模なら可） | 成果物を分割し、各セッションを 25 分で終わる粒度にする |
| 中断リスク | 長い生成は途中で切れうる | ①ファイル単位で独立した DL ボタン ②生成コード自体に進捗ファイル書き込みを義務化 ③「25分で終わらない場合は、完成したファイルだけでも出力せよ」を各プロンプトに明記 |
| データ | v0 は `input/` を取得できない | `docs/data_schema.md`（実データから自動生成）を根拠資料として渡す |
| 実行 | v0 サンドボックスで pandas/LightGBM は動かない前提 | v0 には**検証をさせない**。コード生成に専念させ、実行・計測はローカルで行う |
| 出力 | サンドボックス外に共有 URL は出せない | Write で `deliverables/` に実ファイル化 + React アプリからコピー/個別DL/ZIP一括 DL |
| 応答長 | 1応答が長いとターン強制終了（目安4分/出力量）。ツールを呼ばない応答はターン終了扱い | 全プロンプト §0.5 に作業規約を内蔵（1応答200行・骨格→Edit・`sleep 30`・`__DONE__` 判定・22/25分ルール） |
| 途中中断 | 強制終了時は書き込み済みファイルだけ残る | 再開手順をプロンプトに明記。中断時は `v0/messages/再開用_ターン中断時.md` を送る（最初からやらない） |

## 2. セッション実行順序

```text
S0: リポジトリ・環境・docs・プロンプト整備（ローカル・完了）
S1: P1 特徴量ライブラリ v2        → alpha_features.py をDL → ローカルで truncation 検査
S2: P2 戦略本体 v2               → alpha_v2.py + walkforward_config.json をDL → walk-forward 実行
S3: P3 学習と推論の実装           → train_v2.py + submission.py をDL → 採点（Train/Valid）
S4: P4 診断駆動の改善ラウンド1     → 実測メトリクスを渡し、改善版を生成
S5: P5 改善ラウンド2（アンサンブル・局面配分）
S6: P6 戦略レポート + 最終検収      → README.md（提出用レポート）
```

各セッションの成果物と検収:

| セッション | プロンプト | 成果物 | ローカル検収 |
|---|---|---|---|
| S1 | `P1_特徴量ライブラリv2.md` | `alpha_features.py`, `selftest_features.py` | `py_compile` → `tools/check_truncation.py` → 特徴量の NaN率・分布確認 |
| S2 | `P2_戦略本体v2.md` | `alpha_v2.py`, `walkforward_config.json` | `tools/walkforward.py --strategy ...` → Train OOS Sharpe を比較（**基準: v1 の再現値 +1.993**） |
| S3 | `P3_学習と推論.md` | `train_v2.py`, `submission.py`, `meta_v2.json` | 学習 → `tools/score.py --split valid` → `tools/score.py --split train` → `tools/check_lookahead.py` |
| S4 | `P4_診断と改善1.md` | 改善版モジュール一式 | walk-forward の改善幅・Valid の改善幅を確認 |
| S5 | `P5_改善2_アンサンブル.md` | 改善版モジュール一式 | 同上（過学習に注意。Train OOS と Valid の両方で改善したものだけ採用） |
| S6 | `P6_戦略レポート.md` | `README.md`（提出レポート） | 数値の突合（捏造チェック）→ `tools/make_zip.py --score` |

> 全プロンプトに §0.5「作業の進め方（タイムアウト対策）」を内蔵済み（正本は `v0/prompts/P0_作業規約.md`）。
> 成果物は各プロンプト §0 に従い `deliverables/` に実ファイルとして作り、アプリから回収する。
> 初回メッセージへ作業規約を貼り付ける必要はない。

## 3. フィードバック・プロトコル（各セッション後の5分ルーチン）

1. 成果物を DL → 戦略フォルダへ配置 → `py_compile`
2. ローカルで実行し、**実測メトリクス**を取得（`tools/score.py` / `tools/walkforward.py`）
3. 次セッションの初回メッセージ末尾に以下を追記する:

```text
【前セッションの実測結果（必ず反映せよ）】
- 変更点: <何をしたか>
- Train OOS Sharpe: <before> → <after>
- Valid Sharpe: <before> → <after>（グロス/コスト/回転率も1行で）
- 問題: <動かなかった点・遅すぎた点・NaNが出た点>
- 次の指示: <1〜3行>
```

4. 採用判断は **Train OOS（purged walk-forward）を主、Valid を従**とする。
   Valid だけ良くて Train OOS が悪化した変更は採用しない（レジーム依存の過学習とみなす）。

## 4. 中断対策（25分制限・大規模作業）

- 生成コード側の義務（`docs/coding_conventions.md` §6）:
  - `tools/progress.py` の `Progress` で **ステップごとに JSONL 追記**（`work/progress/*.json`）
  - 学習済みモデルは **1本終わるごとに保存**（`--resume` で既存をスキップ）
  - 失敗時は `prog.failed(...)` を書いてから例外を投げる
- v0 側の義務（各プロンプトに明記）:
  - 応答が 25 分に届きそうなら、**完成済みファイルだけでも先に出力**する
  - 1ファイル=1ダウンロードボタンにし、部分的な回収を可能にする
- ローカル側: 長時間ジョブはバックグラウンド起動＋ログを `work/logs/` へ。
  `python tools/progress.py show work/progress/<name>.json` で進捗確認。
- ターンが最終報告なしで途切れたら、`v0/messages/再開用_ターン中断時.md` を送る。
  作業規約はプロンプト内蔵のため貼り直し不要。2回以上中断したら「今回はファイル X だけ」に分割する。
